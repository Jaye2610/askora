# 4 · 项目完整流程

> 本文把两个最核心的业务旅程完整走一遍：**① 一次用户提问（问答主链路）** 和 **② 一份文档从上传到可被检索（知识生产链路）**。用"谁调谁、传什么、返回什么"的方式讲清楚，含真实的方法/类/模板路径，可直接对着源码核对。

---

## 4.1 旅程一：一次用户提问（问答主链路）

### 起点：`RAGChatController`

前端发起 SSE 请求 `POST /api/askora/rag/chat/stream`，带上 `Authorization`、`question`、`conversationId`(可选)、`deepThinking`。

```
RAGChatController.streamChat(question, conversationId, deepThinking, SseEmitter)
        │
        ▼
RAGChatServiceImpl.streamChat(...)
```

`RAGChatServiceImpl`（`rag/service/impl/`）做四件事：

1. **给标识**：`conversationId` 为空 → `IdUtil.getSnowflakeNextIdStr()` 开新会话；再生成 `taskId`
2. **建回调**：`callbackFactory.createChatEventHandler(emitter, conversationId, taskId)` → 创建 `StreamChatEventHandler`（它构造时立即 `initialize()` 推 `meta` 事件 + 注册任务到 `StreamTaskManager`）
3. **排队限流**：`chatQueueLimiter.enqueue(question, conversationId, emitter, task)` —— Redis 公平排队 + 分布式并发控制，`max-concurrent=10`
4. **执行**（拿到排队许可后）：`traceRunner.run(...)` 用 Trace 包裹，内部构建 `StreamChatContext` 交给 `chatPipeline.execute(ctx)`

---

### 主流水线：`StreamChatPipeline.execute`

这是整个 Agent 的核心，七个阶段顺序执行。我们逐步展开。

```
execute(ctx)
 ├─ 1 loadMemory(ctx)
 ├─ 2 rewriteQuery(ctx)
 ├─ 3 resolveIntents(ctx)
 ├─ 4 handleGuidance(ctx)     → true 则短路结束
 ├─ 5 handleSystemOnly(ctx)   → true 则短路结束
 ├─ 6 retrieve(ctx)
 ├─ 7 handleEmptyRetrieval(ctx) → true 则短路结束
 └─ 8 streamRagResponse(ctx, retrievalCtx)
```

#### 阶段1 · 加载记忆 `loadMemory`
- `memoryService.load(conversationId, userId)` → 历史消息（摘要作为 history[0] system 消息 + 最近 N 轮）
- `memoryService.append(conversationId, userId, user(question))` → **先把当前问题落库**（保证本次不进历史），返回 messageId
- `callback.onReplyToMessageId(messageId)` → 回传前端"回答回复的是哪条问题"

#### 阶段2 · 改写与拆分 `rewriteQuery`
- `queryRewriteService.rewriteWithSplit(question, history)` → 一次 LLM 调用返回 `RewriteResult{rewrittenQuestion, subQuestions}`
- 模板：`prompt/user-question-rewrite.st`；失败回退原问题

#### 阶段3 · 意图解析 `resolveIntents`
- `intentResolver.resolve(rewriteResult)` → 对每个子问题**并行** `intentClassifier.classifyTargets`（LLM 打分）
- 每个子问题：过滤 `score >= INTENT_MIN_SCORE(0.35)`、限 `MAX_INTENT_COUNT(3)`
- 全局再 `capTotalIntents`：每个子问题保底最高分意图，剩余按分补配额
- 结果：`List<SubQuestionIntent>`（每个含 `subQuestion` + `List<NodeScore>`）

#### 阶段4 · 歧义引导 `handleGuidance`（可选短路）
- `guidanceService.detectAmbiguity(rewrittenQuestion, subIntents)`
- 命中歧义 → `callback.onContent(澄清选项)` + `onComplete()`，**短路返回**（不进检索）
- 逻辑（`IntentGuidanceService`）：单子问题 + 至少两个系统级候选 → 规则快判（分数比值/点名系统）→ 边界区间交 `AmbiguityLLMChecker` → 渲染 `guidance-prompt.st`

#### 阶段5 · 纯系统意图 `handleSystemOnly`（可选短路）
- 若所有子问题都满足 `intentResolver.isSystemOnly`（单一 SYSTEM 闲聊意图）
- 则 `streamSystemResponse`：用意图上的自定义 `promptTemplate`（缺省回退 `SYSTEM_CHAT` 槽位），`temperature=0.7`，`thinking=false`，直接流式输出，**短路**

#### 阶段6 · 检索 `retrieve`
- `retrievalEngine.retrieve(subIntents)` → `RetrievalContext{mcpContext, kbContext, intentChunks, eligibleIntentIds}`
- 详见下方"检索内部展开"

#### 阶段7 · 空检索兜底 `handleEmptyRetrieval`（可选短路）
- `retrievalCtx.isEmpty()` → 推"未检索到与问题相关的文档内容。"，短路

#### 阶段8 · 流式回答 `streamRagResponse`
1. `intentResolver.mergeIntentGroup(subIntents)` → `IntentGroup{mcpIntents, kbIntents}`
2. `sourcesAssembler.assemble(intentChunks)` → `List<SourceRef>`（**检索后一次性建立来源编号**）
3. `callback.onSources(sources)`（暂存，FINISH 时下发）+ `citationContextEnricher.enrich`（给 KB 上下文注编号）
4. `groundingChunksAssembler.assemble(...)` → `callback.onGroundingChunks(...)`（落库供推荐追问）
5. `streamLLMResponse`：
   - `promptBuilder.buildStructuredMessages(promptContext, history, question, subQuestions)` → 消息序列
   - `ChatRequest{thinking=deepThinking, temperature=mcp?0.3:0, topP=mcp?0.8:1}`
   - `llmService.streamChat(req, callback)` → 返回取消句柄
6. `taskManager.bindHandle(taskId, handle)` → 支持用户中途停止

---

### 检索内部展开（阶段6 的详解）

```
RetrievalEngine.retrieve(subIntents)
 │  1. 算一次 RetrievalBudget{recallBudget=20, candidateLimit=40, contextTopK=10}
 │     （三段预算单调收窄，配置已在启动时校验）
 │  2. 对每个子问题并行 buildSubQuestionContext（ragContextExecutor）
 │     失败 → 降级空上下文（但保留该子问题的合格意图归因）
 ▼
buildSubQuestionContext(intent, budget)
 ├─ kbIntents = NodeScoreFilters.kb(...)
 ├─ mcpIntents = NodeScoreFilters.mcp(...)
 ├─ retrieveAndRerank(intent, kbIntents, budget)
 │     └─ multiChannelRetrievalEngine.retrieveKnowledgeChannels(intent, budget)
 │           ├─ buildSearchContext (retrievalScopeResolver.resolve → 定向/全局)
 │           ├─ executeSearchChannels: 并行跑启用通道(向量/关键词/图谱/联网)，通道级15s超时
 │           │    每通道失败 → emptyResult(0) 只损失自己
 │           └─ executePostProcessors: 按 order 跑 去重→融合RRF→Rerank
 ├─ mcpContext = (mcpIntents 非空) ? executeMcpAndMerge : ""
 │     └─ executeMcpTools → 每个工具并行（mcpBatchExecutor）：
 │         McpParameterExtractor.extractParameters(question, tool, paramPrompt)
 │         ├─ SUCCESS → executor.execute(params)             （真调用远端）
 │         ├─ NEED_CLARIFICATION → 注入"请向用户追问"提示（不进工具）
 │         └─ FAILED → 注入"参数提取失败跳过"提示
 ▼
 合并子问题上下文 → RetrievalContext
```

**关键点**：
- 向量通道内部：定向（命中库主路 + 未命中库补充路，`supplementRatio=0.25`）或全局（全库），Rerank 前先按候选池截断
- 作用域在**进入通道前一次算好**挂到 `SearchContext`，三通道同源
- 融合：RRF `score = Σ w/(k+rank)`，`rrf-k=20`，通道权重 向量1.0/关键词1.0/图谱0.8/联网0.5
- Rerank：交叉注意力精排到 `contextTopK=10`，输出"图谱证据存活率"归因日志

### 流式输出与 SSE（阶段8 的传输细节）

`StreamChatEventHandler`（`rag/service/handler/`）把 `StreamCallback` 翻译成 SSE：

| 时机 | 事件 | 载荷 |
|:---|:---|:---|
| 构造时 | `meta` | `MetaPayload{conversationId, taskId}` |
| 流式思考增量 | `message` | `MessageDelta{type=think, content}` |
| 流式正文增量 | `message` | `MessageDelta{type=response, content}` |
| 生成完成 | `finish` | `CompletionPayload{messageId, title, sources, status=NORMAL}` |
| 收尾 | `done` | `[DONE]` |
| 取消 | `finish? / error / ...` | `status=INTERRUPTED` 先落库已生成内容 |

增量按 `messageChunkSize`（默认 5 字符）用**码点**切块，避免切坏多字节字符。
`onComplete`：完整回答（含思考/来源/grounding）→ `memoryService.append` 落库为 assistant 消息 → 推 `finish`/`done` → 注销任务 → `sender.complete()`。

## 4.2 旅程二：一份文档从上传到可被检索

### 起点：文档上传

```
KnowledgeDocumentController (POST /knowledge-base/{kb-id}/docs/upload, multipart)
        │
        ▼
KnowledgeDocumentServiceImpl.upload(file, kbId, spec...)
 ├─ SemaphoreInitializer 的信号量（MinerU 等并发控制，可选）
 ├─ OSS/S3 保存原始文件（FileStorageService → ObjectStorageClient）
 ├─ 持久化 KnowledgeDocumentDO（status=PENDING）
 └─ startChunk() → 发 RocketMQ 事务消息
```

### RocketMQ 事务消息（可靠异步）

```
startChunk
 ├─ messageQueueProducer.sendInTransaction(topic=knowledge-document-chunk_topic, ...)
 │     ├─ 发半消息
 │     ├─ 本地事务：把文档 status 置 RUNNING + 注册调度（guarding 并发 chunking）
 │     └─ commit → 半消息转正式；rollback → 消息不投递
 └─ broker 兜底：KnowledgeDocumentChunkTransactionChecker 查文档是否 RUNNING 决定 COMMIT/ROLLBACK
```

### 消费者执行入库内核

```
KnowledgeDocumentChunkConsumer.onMessage(doc)
        │
        ▼
KnowledgeDocumentServiceImpl.executeChunk → runChunkTask
 ├─ VectorTargetResolver.resolve(...)   （partition=collectionName, embeddingModel, dimension）
 ├─ IngestionSpecCodec.read(...)        （读取 JSONB 中的解析/分块规格）
 └─ ingestionKernel.run(doc, bytes, spec, target)   ← 五阶段内核
```

### 五阶段内核 `DefaultIngestionKernel`

```
identity → parse → chunk → embed → index（不可跳过，全链路单事务）
```

1. **identity**：`MimeTypeDetector.detect(bytes, filename)`（Tika），唯一权威
2. **parse**：`ParserRegistry.require(mimeType, parseProfile)` → 各 `DocumentParser.parseStructured(bytes, mimeType)` → `ParsedDocument（有序 List<Block>）`
   - PDF/Word：MinerU（FIDELITY）或 Tika
   - Excel：POI + `ExcelTableNormalizer`（合并单元格/多行表头/超链接/公式）
   - 图片：VLM 图生文 + Batik(SVG) → `ImageBlock`
   - Markdown：commonmark + GFM Tables
3. **chunk**：`ChunkingService.chunk(blocks, budget)` → `BlockAwareChunkerDispatcher`（按 Block 类型选 chunker）→ `ChunkPacker` 按标题章节打包 → `List<Chunk>`
4. **embed**：`ChunkEmbeddingService.embed(chunks, target)` → `EmbeddingService.embedBatch`（infra-ai 路由），校验向量维度 == 部署维度
5. **index**：`ChunkIndexWriter.replaceDocument` → `ChunkSink` 扇出：
   - `RelationalChunkSink` → `t_knowledge_chunk`（content/contentHash/tokenCount/embeddingText）
   - `VectorChunkSink` → `VectorStoreService`（装饰器链：Graph 同步 → Keyword 同步 → PG/Milvus）
   - **同一 Spring 事务**，失败整体回滚

### 入库后的同步旁路
每个向量写入会经历 `VectorStoreService` 的**装饰器链**：
- `KeywordSyncingVectorStoreService`：同步到 ES 关键词索引（`rag_keyword_store`）
- `GraphSyncingVectorStoreService`：同步到 LightRAG 图谱

### 知识库删除的异步清理
```
KnowledgeBaseServiceImpl.delete
 ├─ 校验：有文档则拒绝
 └─ 发 RocketMQ 事务消息(knowledge-base-cleanup_topic)
       └─ KnowledgeBaseCleanupConsumer 异步回收：向量空间/存储桶/ES索引/图谱数据（best-effort+重试）
```

### 定时刷新（URL 源）
`KnowledgeDocumentScheduleJob`（`@Scheduled`）扫描 `t_knowledge_document_schedule`，对启用调度的 URL 文档按 cron 重新拉取解析入库。

## 4.3 两条链路如何交汇

- **生产侧**（旅程二）产出：关系库 `t_knowledge_chunk` + 向量库 + ES 索引 + 图谱
- **消费侧**（旅程一）检索时，`VectorSearchChannel` 查向量库、`KeywordSearchChannel` 查 ES、`GraphSearchChannel` 查图谱、`WebSearchChannel` 联网
- 检索命中 → `RetrievedChunk` → RRF/Rerank → 净化为 `kbContext` → 进入 `Prompt` → LLM 回答
- 回答落库为 `ConversationMessageDO`（带 `sources`/`retrievedChunks`），供来源面板、推荐追问、人工反馈复用

**一句话闭环**：文档进 → 多路索引 → 用户问 → 意图定位 → 多路召回 → 融合精排 → 带证据回答 → 回答存证 → 反馈回流优化。

## 4.4 完整方法调用链速查（一屏）

**问答链**：`RAGChatController → RAGChatServiceImpl → ChatQueueLimiter → StreamChatTraceRunner → StreamChatPipeline → (memory→rewrite→intent→guidance→retrieve→rag) → LLMService/RoutingLLMService → ModelRoutingExecutor → ModelHealthStore → ChatClient`

**检索链**：`RetrievalEngine → MultiChannelRetrievalEngine → {Vector/Keyword/Graph/Web}SearchChannel → {Dedup→Fusion→Rerank} → contextFormatter`

**入库链**：`KnowledgeDocumentController → KnowledgeDocumentServiceImpl → [RocketMQ事务消息] → KnowledgeDocumentChunkConsumer → DefaultIngestionKernel → ParserRegistry/DocumentParser → ChunkingService → ChunkEmbeddingService → ChunkIndexWriter → {Relational,Vector}ChunkSink`

**模型路由链**：`RoutingLLMService → ModelRoutingExecutor.executeWithFallback → ModelHealthStore.allowCall / markSuccess / markFailure → {BaiLian,SiliconFlow,AIHubMix,Ollama}ChatClient → OpenAIStyleSseParser`
