# 5 · 企业级演进路线

> 本项目本身就是一条"从 demo 到企业级"的真实演进史（751 次提交，2025-11 → 2026-08）。本文把这条演进抽象成**可复用的升级路线**：每阶段解决什么问题、用什么手段、演进到下一阶段的动因。你可以用它对照自己的项目定位，也能在介绍项目时讲清"为什么长这样"。

## 5.2 L0 → L1：从"盲查"到"懂问题"

**痛点**：直接拿用户原话去向量库查，措辞一变就搜不准；多轮对话没有历史，上下文断裂。

**演进手段**：
1. **查询改写**（`QueryRewriteService`）：LLM 把口语改为检索友好的查询
2. **多问句拆分**（`rewriteWithSplit`）："帮我查 A 和 B" 拆成两个子问题分别检索
3. **树形意图识别**（`IntentResolver` + `IntentClassifier`）：把问题映射到 DOMAIN→CATEGORY→Leaf 意图，命中即定检索范围
4. **会话记忆**（`ConversationMemoryService`）：最近 N 轮 + LLM 摘要

**下一阶段动因**：意图能定范围了，但"意图本身判错了怎么办"？→ 引出歧义澄清（L3 的 `IntentGuidanceService`）和检索作用域补充路。

---

## 5.3 L1 → L2：从"只有文本"到"多模态知识生产"

**痛点**：企业文档是 PDF/Word/Excel/图片/表格，不是干净的 txt；粗糙切片会切断标题/表格/代码。

**演进手段**：
1. **结构化解析**（`core/parser`）：Tika/POI/CommonMark/MinerU/VLM，解析成有序 `List<Block>`
2. **块感知分块**（`core/chunk/blockaware`）：按 Block 类型选 Chunker（标题/代码/表格/HTML表格/图片），`ChunkPacker` 按标题章节打包，`TextSplitter` 边界感知切分
3. **多模态索引**：图片 VLM 图生文入向量；Excel 表格归一化
4. **RocketMQ 事务消息**：把重活（解析/分块/向量化）异步化，保证库状态与消息最终一致

**下一阶段动因**：文本/向量都好了，但用户问法仍可能跨多个知识库、或要在全网找答案 → 引出多路检索与模型高可用（L3）。

---

## 5.4 L2 → L3：从"单路"到"多路检索 + 模型治理"

### 5.4.1 多路检索
演进路径（每一步都对应真实提交）：
- 单路向量 → 向量+关键词（`461d796` ES BM25）→ 知识图谱（`173f17a` LigRAG）→ 联网（`6a1ecf7` You.com）
- **为什么要多路**：向量管语义但丢了精确术语，BM25 管词面但不懂语义，图谱管实体关系，联网管时效。四者互补。
- **怎么融合**：RRF（跨模态名次可比）+ 加权 + Rerank 精排（`e7ef262` 去重合并、`9a65b76` 消除 topK 多义性按第一性原理解释配置）
- **怎么管"查哪些库"**：检索作用域 `RetrievalScopeResolver`（定向/全局/补充路），`cf5ffa6` 全局跨 collection 召回

### 5.4.2 模型治理（高可用）
- **多供应商 + 档位**（`f104042`）：fast/standard/deep 三档，每档多个候选模型
- **模型路由 + 故障转移**（`ModelRoutingExecutor`）：候选按优线性降级
- **三态熔断**（`ModelHealthStore`）：CLOSED/OPEN/HALF_OPEN，按 targetId 独立隔离
- **首包探测**（`LlmFirstPacketProbe`）：流式响应万一不出字，提前降级；`9509b02` 修复半开名额释放
- **空白响应拒绝 + 触发降级**（`3bfb3d7`）

**下一阶段动因**：检索/模型都稳了，但"生产落地"还需要闭环：看得见链路、能追来源、能反馈、能审计、能配置 → 引出 L4。

## 5.5 L3 → L4：从"可用"到"可生产、可运营、可演进"

### 5.5.1 可观察性（Trace）
- `@RagTraceNode` 每个环节埋点，`RagTraceContext`（TTL）跨异步线程传 traceId
- `StreamChatTraceRunner` 流式链路追踪，前端 Trace 详情页（`89b49cf` DFS 展开）
- 归因日志：Rerank 前后按通道统计候选存活（图/关键词贡献一目了然）

### 5.5.2 推荐追问与来源
- `RecommendedQuestionGenerator`：依据 grounding 片段生成"你可能还想问"
- `CitationContextEnricher`：回答行内引用角标 `[N]`，`ab31f8f` 支持来源文档预览

### 5.5.3 管理与审计
- `17eaaa6` 智能体管理（AgentProfile/Prompt 槽位）
- `951d813` 审计日志（bizlog-sdk，`@LogRecord` 操作人/快照/diff）
- Dashboard（`admin/`）KPI/性能/趋势聚合
- 配置校验（`ChatTierConfigValidator`/`RetrievalConfigEnvironmentPostProcessor`）启动即失败，防配置事故

### 5.5.4 人机协同（MCP / Agent 化方向）
- 独立 `mcp-server` 暴露工具（天气/搜索/报表/工单）
- 主应用 `McpToolRegistry` 集成 MCP 工具，`RetrievalEngine` 对 MCP 意图做工具调用
- 配置档位 `askora.engine.type=workflow | agent`（**workflow** = v1 编排管线；**agent** = v2 ReAct 架构，RAG 管线降级为主 Agent 的一个 Tool）——**这就是项目名字从"RAG"往"Agent"演进的最明确信号**

---

## 5.6 演进原则（可复用方法论）

1. **每阶段只解决一个真痛点**，由生产问题驱动，不提前做宏大设计
2. **分层引入**：infra-ai 模型层 → bootstrap 编排层，依赖单向，边界清晰
3. **配置兜底**：新能力默认关（如图谱/联网通道 `enabled=false`），配置校验启动期失败，避免带病上线
4. **可观察优先**：先埋点再上线，归因日志是后续调优的抓手
5. **兼容演进**：升级脚本按版本目录（`resources/database/upgrades/`）累积，老库可增量升级

## 5.7 如果是新项目，怎么按这条路线走

1. **先用一个能跑的最小闭环**：向量检索 + 直接回答（L0）
2. **再补"懂问题"**：改写 + 意图 + 记忆（L1）——这一层 ROI 最高
3. **再补"吃文档"**：多模态解析 + 块感知分块 + 异步入库（L2）
4. **再补"稳"**：多路检索融合 + 模型多供应商熔断降级（L3）
5. **最后补"可运营"**：Trace、来源、反馈、审计、后台、配置校验（L4）
6. **面向未来**：把能力抽象成 Tool/MCP，往 Agent 编排演进（engine.type=agent）

> 每步都让"它比上一步更能回答好真实问题"——这是这条路线被证明有效的根本。
