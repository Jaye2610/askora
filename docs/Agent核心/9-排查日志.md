# 9 · 排查日志

> 本文解决"**线上/本地出问题了怎么查**"。它既是排查方法论，也收录了我在本仓库实测跑通过程中遇到的真实问题与解决过程（第一手记录）。比"踩坑日志"更偏"操作手册"：给出现象 → 看什么日志 → 看哪个配置 → 动哪个开关。

---

## 9.1 排查前的心态与总原则

1. **先复现，再动手**：记录现象 + 时间点 + 都在哪一步
2. **从日志分层定位**：应用日志（`-Dlogging` 或 stdout）→ RocketMQ 消费日志 → 中间件日志
3. **配置先于代码怀疑**：本项目大量行为由 `application.yaml` 控制，先确认配置是否符合预期（详见"配置自检"）
4. **善用"检索归因"日志**：检索相关的怪问题，第一条线就是它
5. **善用 Trace**：`rag.trace.enabled=true` 时，前端/后台能看到每个环节耗时

---

## 9.2 配置自检（80% 问题的第一现场）

启动/运行异常时，先核对 `application.yaml` 这几组：

| 配置段 | 若不对会怎样 | 正常参考 |
|:---|:---|:---|
| `rag.vector.type` | pg/milvus 不一致导致查不到向量 | `pg`（本仓库） |
| `rag.keyword.type` | 配了 es 但 ES 未起 → 关键通道失败 | `none` 可关 |
| `rag.graph.type` | 图谱后端未起 | `none` 可关 |
| `rag.search.channels.*.enabled` | 通道开关 | vector=true，keyword/graph/web 默认 false |
| `rag.search` 漏斗预算 | 三段单调收窄校验 | recall≥topK≤candidate |
| `ai.chat.candidates/tiers` | 候选模型不可用 | 至少一个可用 |
| `spring.datasource/redis/rocketmq` | 中间件连不上 | 127.0.0.1 默认 |

**快速命令**：
```bash
# 看配置物化结果（需登录 token）
curl -s http://127.0.0.1:9090/api/askora/rag/settings -H "Authorization: $TOKEN"
```

## 9.3 日志能告诉你什么（关键日志速查）

### 聊天 / 检索
| 日志关键字 | 含义 |
|:---|:---|
| `启用的检索通道：` | 本次实际跑了哪几个通道 |
| `执行检索通道：` + `通道 ... 完成 ✓...N 个 Chunk` | 各通道召回 |
| `通道 ... 超过通道级超时` | 该通道被降级（最慢一路） |
| `后置处理器 ... 完成 - 输入/输出` | 去重/融合/Rerank 变化 |
| `检索归因 - 融合池按通道 / 送入 Rerank 按通道` | 融合候选分布 |
| `检索归因 - 图谱证据存活: x/y` | 图谱通道是否纯成本 |
| `子问题上下文构建失败，降级为空上下文` | 某子问题降级（不影响其它） |

### 模型
| 日志关键字 | 含义 |
|:---|:---|
| `chat 档位配置校验通过` | 档位合法 |
| `... model failed, fallback to next` | 候选降级 |
| `... provider client missing` | 某供应商没配 key |
| `All CHAT model candidates failed` | 全部候选失败（全局降级）|

### 入库
| 日志关键字 | 含义 |
|:---|:---|
| `解析器注册表就绪` | 解析器装载/自检 |
| `MinerU 分布式解析限流初始化` | MinerU 并发控制 |
| `对象存储桶就绪 bucket=` | S3/MinIO 桶 |
| `向量共享空间就绪 collection=` | 向量空间 |
| `Register the listener ... containerName:` | RocketMQ 消费者 |

### 启动
| 日志关键字 | 含义 |
|:---|:---|
| `Started AskoraApplication in ...` | 启动成功 |
| `Tomcat started on port 9090 ... context path '/api/askora'` | Web 就绪 |
| `连接 MCP Server ... 失败，跳过` | MCP 未起（可忽略 WARN）|

## 9.4 实战排查记录一：编译不过（第一手）

**场景**：`./mvnw clean compile` 失败，`infra-ai` 报：
```
找不到符号 类 HttpResponseHelper
位置: 程序包 io.github.jaye.ai.askora.infra.http
```
（出现在 `AbstractOpenAIStyleChatClient` / `AbstractOpenAIStyleEmbeddingClient` / `BaiLianRerankClient` / `RoutingVlmService`）

**排查步骤**：
1. 先看 Reactor：`framework` 成功、`infra-ai` 失败 → 问题在 `infra-ai`
2. 看报错位置 import：`io.github.jaye.ai.askora.infra.http.HttpResponseHelper`
3. 找该文件实际 package 声明：
   ```bash
   grep -rlE "^package io\.github\.jaye\.(?!ai)" infra-ai/src/main/java --include=*.java -P
   # 命中: infra-ai/.../http/HttpResponseHelper.java  → package io.github.jaye.infra.http;
   ```
4. **结论**：包结构重构后该文件 package 声明没跟上（仍是旧 `io.github.jaye.infra.http`），与它自己 import 的 `ai.askora.infra.*` 不一致，导致同类在不同包，编译找不到

**修复**：把该文件 `package` 对齐为 `io.github.jaye.ai.askora.infra.http` → 全量编译通过。

**经验**：大范围包重命名后，用 `grep -P "^package io\.github\.jaye\.(?!ai)"` 全仓扫一遍"没跟上的旧包声明"，是快速自检手段。

## 9.5 实战排查记录二：应用启动（第一手）

**场景**：启动后端。

**步骤与结果**：
1. 确认中间件：`docker ps` 看 PG/Redis/RocketMQ/MinIO 是否 In 起来（可复用 `docker start <容器>`）
2. 确认数据库 schema：`docker exec askora-pg psql -U postgres -d askora -c "\dt"`（应见 24 张表，含 `t_knowledge_vector`）
3. 打包：`./mvnw -DskipTests package`
4. 启动：`java -jar bootstrap/target/bootstrap-0.0.1-SNAPSHOT.jar`
5. 观察成功标志：`Tomcat started on port 9090`、`Started AskoraApplication in 20.1 seconds`
6. 验证接口：`POST /auth/login` 应返回 `{"code":"0",...token...}`；`GET /rag/settings`、`GET /admin/dashboard/overview` 应 `code="0"`

**过程中观察到的非致命现象**：
- `连接 MCP Server [default] 失败，跳过工具注册`（WARN）：因为 `mcp-server` 没起（9099）。**不影响主应用**，是设计上的可选能力
- 若你不想要 MCP，可关 `rag.mcp.servers` 或不起 mcp-server

**一个小坑（git-bash 后台）**：在 git-bash 里用 `java -jar ... &` 后台化，进程会随 shell 结束被杀、日志为空。改用**前台**或轮询读日志文件即可。

## 9.6 专项排查：某个模型一直失败 / 被熔断

**目标链**：`RoutingLLMService → ModelRoutingExecutor → ModelHealthStore`

**步骤**：
1. 看日志是否重复 `model failed, fallback to next. modelId=...`
2. 查配置 `ai.chat.candidates/tiers`，确认该候选是否还被引用
3. 若怀疑"半开名额占用"（曾修 `releaseHalfOpenPermit` 坑）：看该 target 是否一直 `provider client missing` 或持续熔断
4. 用 `ai.selection.failure-threshold(2)` / `open-duration-ms(30000)` 调熔断灵敏度
5. 确认 API key：`BAILIAN_API_KEY` / `SILICONFLOW_API_KEY` / `AIHUBMIX_API_KEY` / Ollama `http://localhost:11434` 可达

---

## 9.7 专项排查：检索不到内容 或 结果质量差

**步骤**：
1. **先看归因日志**：`启用的检索通道` → `各通道 Chunk 数` → `融合池按通道` → `送入 Rerank 按通道`。哪个通道没参与/被截没，一看便知
2. 确认**作用域**：定向/全局。若定向但意图判错，样本库证据全丢 → 看是否需要调 `scope.confidence-threshold(0.6)` 或 `supplement-ratio(0.25)`
3. 确认**漏斗预算**是否单调收窄：`recall-budget(20) ≥ default-top-k(10) ≤ rerank-candidate-limit(40)`
4. 确认向量空间/Embedding：`ai.embedding` 是否有可用候选；`rag.default.dimension(1536)` 与模型一致
5. 若开了图谱/关键词：看通道存活率，可能需要降 `fusion.channel-weights.graph`

---

## 9.8 专项排查：入库没成功 / 向量没写入

**步骤**：
1. 看文档 `status`（`t_knowledge_document`）：PENDING/RUNNING/FAILED
2. 看 RocketMQ 消费者日志是否 `Register the listener ... knowledgeDocumentChunkConsumer`
3. 看入库内核阶段计时：`KnowledgeDocumentChunkLogDO`（extract/chunk/embed/persist）
4. 确认 `t_knowledge_vector` 有数据；确认 `VectorStoreService` 装饰器链（Graph/Keyword 同步）未因下游挂掉阻塞
5. 图片/复杂 PDF：看是否被 MinerU 信号量限流、`MINERU_API_KEY` 是否配

---

## 9.9 专项排查：多轮对话"变傻" / 记忆丢了

**步骤**：
1. 看 `ConversationSummaryDO` 摘要是否生成
2. 看 `rag.memory`：`history-keep-turns(8)`、`summary-enabled/start-turns/max-chars`
3. 确认消息落库：`t_message` 相关（`alert`: 实际消息可能是 `t_message` 或 `t_conversation_message`，以 `\dt` 实际表为准）
4. Trace 里看每次 `loadMemory` 返回的历史条数与摘要内容

## 9.10 排查工具箱（命令速查）

```bash
# 后端实时日志（若用 nohup/后台）
tail -f <app.log>

# 中间件健康
docker ps | grep -E "askora|rmq"
docker exec askora-pg pg_isready -U postgres
docker exec askora-redis redis-cli -a 123456 ping

# 数据库直接看状态（排查入库/会话）
docker exec askora-pg psql -U postgres -d askora -c "select id,name,status from t_knowledge_document order by create_time desc limit 10"

# 配置物化
curl -s .../rag/settings -H "Authorization: $TOKEN"

# 归因 / 通道日志关键字抓取
tail -f <app.log> | grep -E "检索归因|启用的检索通道|fallback|熔断"
```

> 这个项目最大的排查资产，是**把"归因"和"存活率"打到了日志里**——绝大多数检索质量问题，都能从两行 structured log 直接定位，而不需要抓包。这是最值得模仿的一点。
