# 8 · 变化原因（为什么这么设计 / 为什么改）

> 本文回答"**为什么**"。不只是描述每个类，而是解释**每个关键设计背后真实的问题与权衡**。绝大多数都能在本仓库 git 提交信息中找到原始动机。读懂"为什么"，比背"是什么"更能支撑你在面试/评审里讲深。

---

## 8.1 为什么多模块（bootstrap/framework/infra-ai/mcp-server）？

**问题**：单包结构下，"模型怎么调"和"业务怎么编排"耦合，改一家供应商要牵连整个业务。

**设计**：
- `framework` 抽公共件（约定/上下文/异常/ID/幂等/MQ 封装），业务无关
- `infra-ai` 抽模型层，向 `bootstrap` 提供统一能力
- 依赖单向：`bootstrap → {framework, infra-ai}`，禁止反向

**为什么不是更早拆**：项目是从单体起步演进的（git 最早是单包结构），**到一定复杂度才拆，避免早期过度设计**。这是可复用的演进判断。

---

## 8.2 为什么用"意图树 + 打分"而不是"关键词路由"或"直接全库检索"？

**问题**：企业有多个知识库（人事/财务/开票/产品）。直接全库检索：噪声大、慢、命中差。纯关键词路由：不懂语义。

**设计**：维护一棵 DOMAIN → CATEGORY → Leaf **意图树**，LLM 对问题给节点打分（`score`），命中哪个意图就只查它绑定的 Collection。

**权衡**：意图树需要**人工维护**（管理端 `IntentTreeController` 可配），但换来的是"检索范围精准 + 每库可以配专属 prompt/参数"。这是一次"工程可维护性 vs 检索精度"的交换，对企业多库场景是划算的。

---

## 8.3 为什么需要"歧义澄清"？意图都判了还要澄清？

**问题**：意图打分本身会判错——两个库得分接近时（如"报销"既可能是人事也可能是财务），直接检索可能检错库。

**设计**：`IntentGuidanceService` 在分数比值落在边界区间时，**不检索**，而是让用户二选一。

**为什么好用**：一次澄清问题的成本，远低于"检索错误知识库 → 答错 → 用户重复提问"的往返成本。

**为什么还要 LLM 确认**：规则快判（比值/点名系统）能覆盖大部分明确场景；只有比值落在 `[threshold-margin, threshold)` 的**灰色地带**，才调一次 LLM 做语义确认，控制 LLM 调用成本。

---

## 8.4 为什么检索要"多通道 + RRF + Rerank"三段式？

**问题**：单一检索手段各有致命短板——
- 向量（余弦）：懂语义但拼写敏感、精确术语差
- BM25（关键词）：精确但完全不懂语义
- 图谱：懂实体关系但召回稀疏、证据长
- 联网：懂时效但噪声大

**设计**：四路并行召回 → **RRF 融合**（只看名次，天然解决分数量纲不可比）→ **Rerank 精排**（交叉注意力最终收敛）。

**为什么 RRF 而非加权平均分**：向量余弦 0~1 与 BM25 的得分分布在量纲、分布上完全不同，直接加权没有物理意义；RRF 只用"第几名"，跨模态可比。这是 RRF 在行业内被选中的根本原因。

**为什么 Rerank 不省**：RRF 是便宜粗排，Rerank 是贵精排；两者配合才在**成本与精度**间取平衡。候选池用 `rerank-candidate-limit` 截断控制 Rerank 成本。

---

## 8.5 为什么引入"检索作用域"（定向/全局/补充路）？

**问题**：意图判对时只该查命中库（省又准）；但**意图一旦判错，正确证据只在"未命中库"里**，定向检索就漏了。

**设计**（`RetrievalScopeResolver`）：
- KB 意图最高分 ≥ 0.6 → **定向**：只查命中库
- 否则 → **全局**：跨全库
- 定向时并行补一路"未命中库"，给固定候选名额（`supplement-ratio=0.25`）

**为什么敢在定向时补未命中库**：意图判错与否事前不可靠判定（分数未校准），所以**不判定、直接给补充路固定名额**，交给下游 Rerank 收敛。这是"用一段兜底额度换鲁棒性"的设计。

---

## 8.6 为什么向量通道"定向/全局合一"而不拆两条？

**问题**：早期拆成两条并列通道，同一份证据在 RRF 里被算了两次，自我加权。

**设计**：`VectorSearchChannel` 单通道，内部按作用域分流。

**为什么**：向量与关键词/图谱是"不同模态"可以并列融合；但"定向与全局"只是**同一查询在不同库集合上的范围差异**，是同模态，拆开就是重复计数。（提交 `1c40cdd` 明确记录了这条动机）

---

## 8.7 为什么模型层要"多候选 + 三态熔断 + 线性降级"？

**问题**：任何单一模型供应商/模型都可能：
- 超时 / 限流 / 返回错误 → 单点故障
- 临时变慢 → 首字延迟拉高体验

**设计**：
- 每能力（CHAT/EMBEDDING/RERANK）配**多个候选**（`AIModelProperties`）
- `ModelRoutingExecutor` 按优先级线性降级：失败就换下一个
- `ModelHealthStore` 三态熔断，**按 targetId 独立隔离**（一个熔断不牵连其它）

**为什么三态不是两态（成功/失败）**：两态熔断一旦打开，服务恢复后仍长期拒绝（"熔断冻结"）。引入 HALF_OPEN **探活**：冷却结束后放行一个探测请求，成功即恢复 CLOSED，失败再回 OPEN。这是 Circuit Breaker 标准做法。

**为什么按 targetId 隔离而不是全局**：不同模型健康状态独立，一个坏了不该让所有请求都走降级。

---

## 8.8 为什么会话记忆要"最近 N 轮 + 摘要"两层？

**问题**：全量历史进 prompt → token 成本爆炸；只留最近 N 轮 → 早期关键上下文丢失。

**设计**：最近 `history-keep-turns=8` 轮原始消息 + 超过阈值后触发一轮 LLM **摘要**（`summary-max-chars=400`），摘要作为 history[0] system 消息。

**为什么摘要不每轮调**：摘要只在该滚动到需要更新时生成（`807d422`），否则每轮都调 LLM 白白增加延迟成本。

---

## 8.9 为什么入库用 RocketMQ 事务消息？

**问题**：入库是重活（解析/分块/向量化），不能在 HTTP 请求线程里做；但"异步化"又带来一致性问题——消息发出去了库里没数据，或反了。

**设计**：RocketMQ 事务消息：
1. 发半消息
2. 本地事务把文档置 RUNNING
3. commit → 半消息转正式；rollback → 不投递
4. broker 拿不准时反向 `TransactionChecker` 查文档状态决定 COMMIT/ROLLBACK

**为什么不是普通消息**：普通消息没有"本地事务状态"的保证，要么丢、要么重复，入库这种强一致场景不合适。

---

## 8.10 为什么分块要做"块感知"而不是定长切？

**问题**：定长切片会切断标题、表格列、代码块——检索时上下文残缺。

**设计**：解析成结构化 `Block`（标题/段落/代码/表格/图片/列表/HTML表格），`BlockAwareChunkerDispatcher` 按类型选 `Chunker`，`ChunkPacker` 以标题为边界做**章节级打包**，`TextSplitter` 边界感知切割。

**为什么**：分块的粒度与边界的质量，直接决定 RAG 命中质量。这是"入库质量决定检索上限"的第一性原理。

---

## 8.11 为什么全部用 TransmittableThreadLocal？

**问题**：RAG 全链路大量 `CompletableFuture`/线程池并行（意图并行、通道并行、子问题并行），普通 `ThreadLocal` 在跨线程时**丢失** `UserContext`/`TraceContext`。

**设计**：`TransmittableThreadLocal`（TTL，阿里）配合 `TtlExecutors` 包装的线程池，让用户/追踪上下文**穿透异步边界**。

**为什么不是手动传参**：链路深、参数多（userId/traceId/taskId），手动传参容易漏且污染方法签名，TTL 是更优雅的横切方案。

---

## 8.12 为什么配置文件校验在"启动期"就失败？

**问题**：检索漏斗三段预算如果配成 `recall-budget < default-top-k`，或 Rerank 候选池小于最终条数，运行期才暴露，表现为"检索结果缺失/异常"，极难排查。

**设计**：`RetrievalConfigEnvironmentPostProcessor` + 各 `*Validator` 在启动时校验，违规**启动即失败**（fail fast）。

**为什么**：配置错误是"一旦上线就很贵"的一类事故。启动期内角色发现，比线上灰度期发现便宜一个量级。

---

## 8.13 为什么叫"Askora"、为什么往 Agent 演？

**原由**：项目名定为 **Askora**（Ask 提问 + Ora 智慧之源），突出“从文档入库到智能问答”。`askora.engine.type=workflow | agent` 档位里：
- **workflow** = v1 编排管线（当前默认，确定性流水线，容易测试/观察）
- **agent** = v2 ReAct 架构，RAG 管线降级为主 Agent 的一个 Tool（未来方向，更灵活）

**为什么保留两种**：workflow 确定、易控、适合生产稳定；agent 灵活但更"黑盒"、难测。两者并存让项目能在**稳妥与灵活**间随业务切换，而不是激进重写。这本身就是"企业级演进"的稳健姿态。

## 8.14 变化原因总表（一句话）

| 变化 | 根本原因 |
|:---|:---|
| 多模块化 | 解耦"模型能力"与"业务编排"，防扩散 |
| 意图树 | 多库精准路由，可配专属 prompt/topK |
| 歧义澄清 | 一句澄清 < 检错库往返 |
| 多路检索+RRF+Rerank | 单模态有致命短板，两阶段兼顾成本与精度 |
| 检索作用域定向+补充 | 意图判错时兜底，不丢正确证据 |
| 向量合一通道 | 同模态拆两路会在 RRF 自我加权 |
| 三态熔断+降级 | 单一模型不可靠，需隔离故障与自动恢复 |
| 两层记忆 | 控 token 且保留早期关键上下文 |
| 事务消息 | 异步入库又要强一致 |
| 块感知分块 | 分块边界决定 RAG 命中上限 |
| TTL | 跨异步边界不丢用户/追踪上下文 |
| 启动期校验 | 配置事故越早上线越贵 |
| workflow/agent 并存 | 稳定与灵活按需切换，不激进重写 |
