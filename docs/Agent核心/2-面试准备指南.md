# 2 · 面试准备指南

> 面向要在面试里讲清楚这个项目的人。这里不是"背答案"，而是给出一套**可被追问到底**的理解框架。面试官最在意的不是"你用了什么技术"，而是"**为什么这么设计、遇到什么坑、怎么权衡**"。每节都给出：考点 → 追问 → 答案要点。

---

## 2.1 三十秒电梯陈述

"这是一个面向 **Agentic RAG 演进**的生产级智能问答平台，Java 17 + Spring Boot 3 多模块。核心是 `StreamChatPipeline` 一条流水线串起：**会话记忆 → 查询改写/拆分 → 树形意图识别 → 歧义澄清 → 多路检索（向量/关键词/图谱/联网）→ RRF 融合 + Rerank 精排 → Prompt 组装 → SSE 流式输出**。配套完整知识生产链路（解析/分块/向量化落库）和工程底座（模型三态熔断降级、Redis 公平排队限流、事务消息、链路追踪、审计），是从 demo 到生产真实工程化的一个完整样例。"

## 2.2 架构分层（必考）

**问：项目怎么分层？**
答：四个 Maven 模块，职责边界非常清晰：
- **bootstrap**：主应用，承载所有业务编排（RAG 大脑、知识生产、鉴权、后台）
- **framework**：与业务无关的公共底座——统一 `Result` 约定、`UserContext/TraceContext` 线程上下文、异常体系、错误码、分布式雪花 ID、幂等、缓存、RocketMQ 封装
- **infra-ai**：**模型接入层**——把不同供应商（百炼/硅基/AIHub/Ollama）封装成统一接口，上层再加档位路由、熔断、首包探测、Rerank、Embedding、VLM
- **mcp-server**：独立的 MCP 工具服务器（Streamable HTTP，端口 9099）

**追问：为什么不写在一个大包里？**
答：三个动机——① 依赖方向清晰：`bootstrap → framework/infra-ai`，禁止反向；② infra-ai 复用性强，未来可独立部署成模型网关；③ 编译边界保证团队不互相污染。

## 2.3 Agent 主链路（核心考点，必须倒背如流）

**问：一次问答请求从进来到出去的完整流程？**

答：`RAGChatController` 暴露 SSE 接口 → `RAGChatServiceImpl.streamChat`：
1. 无会话 ID 就生成雪花 ID（新会话）
2. 创建 `StreamChatEventHandler`（SSE 回调，先推 `meta` 建立会话）
3. **`ChatQueueLimiter` 入队限流**（Redis 公平排队 + 分布式并发控制）
4. `StreamChatTraceRunner` 包裹（链路埋点，跨异步线程传递 Trace 上下文）
5. `StreamChatPipeline.execute` 主流程：
   - `loadMemory`：加载历史（最近 N 轮 + 摘要）→ **先落库当前问题**（避免本次进历史）
   - `rewriteQuery`：结合历史改写 + 多问句拆分
   - `resolveIntents`：每个子问题并行做**意图识别**（LLM 打分）
   - `handleGuidance`：若歧义（分数比值落在边界区间）→ 生成澄清选项，**短路结束**，不回检索
   - `handleSystemOnly`：若所有子问题都命中系统类闲聊意图 → 直接系统应答，**跳过检索**
   - `retrieve`：`RetrievalEngine` 综合知识库多通道 + MCP 工具结果
   - `handleEmptyRetrieval`：什么都检索不到 → 提示语，短路
   - `streamRagResponse`：组装引用来源/grounding → 构建 Prompt → LLM 流式输出（思考 + 正文），完成后落库、推 `finish`/`done`

**追问：为什么"先落库当前问题再加载历史"？**
答：保证本次提问**不进历史**，否则上一轮自己会成为这一轮的上下文，污染改写与检索。落库返回的 messageId 回传前端，用于建立"回答→问题"的关联。

## 2.4 意图识别与问题理解（高频深挖）

**问：意图识别在这里解决什么问题？**
答：**避免"把一个问题拿去所有知识库盲查"**。通过 LLM 把问题映射到一棵**意图树**的节点上（Domain 业务域 → Category 系统 → Leaf 意图），命中哪个意图就只检索它绑定的知识库 Collection，精准定位，减少错误召回的噪声、省查询成本。

**追问：怎么实现的多问句拆分 + 意图识别？**
答：`QueryRewriteService` 用一次 LLM 调用同时返回"改写后单句 + 子问题列表"（模板 `prompt/user-question-rewrite.st`）。然后 `IntentResolver` 对**每个子问题并行**做分类（`CompletableFuture` + 专用线程池），每个子问题内部按 `INTENT_MIN_SCORE(0.35)` 过滤、限 `MAX_INTENT_COUNT(3)`。

**追问：意图太多怎么限额？**
答：`capTotalIntents` 三段式——先看总数是否超 `MAX_INTENT_COUNT`；超了则**每个子问题保底保留一个最高分意图**，剩余配额按分数从高到低补；避免某次多问题查询把意图撑爆、也保证每个问题都不被饿死。

**追问：歧义澄清是怎么做的？**
答：`IntentGuidanceService` 分两层：**规则快判**（前两名分数比值：明确则跳过、超过阈值则判歧义；用户问题点名了某个系统名也跳过）+ **LLM 语义确认**（落在边界区间时再调一次 LLM）。命中歧义就渲染"1) 路径A\n2) 路径B"的澄清选项推给用户让其一选。**本质是"让用户花一句话点明，比检索一堆无关证据更省"。**

## 2.5 多通道检索 + 融合精排（核心深挖）

**问：检索有哪几个通道？**
答：`MultiChannelRetrievalEngine` 并行执行所有 `SearchChannel` Bean：**VectorSearchChannel**（向量）、**KeywordSearchChannel**（ES BM25）、**GraphSearchChannel**（LightRAG图谱）、**WebSearchChannel**（联网）。每个通道有独立开关，通道级 `timeoutMs`（默认15s）超时降级为空结果，**最慢一路不能拖垮整体**。

**问：怎么处理"该查哪些库"？**
答：`RetrievalScopeResolver` 按**意图最高分**判定作用域：
- 定向（directed）：KB 意图最高分 ≥ confidence-threshold(0.6)，只查命中意图绑定的库
- 全局（global）：否则退化全库检索
- 定向时还会并一路"**未命中库**"补充通道（`supplement-ratio` 0.25），兜底意图判错的场景

**追问：怎么**融合**多路结果？**
答：`FusionPostProcessor` 用 **RRF（Reciprocal Rank Fusion）**：`score(chunk)=Σ weight/(k+rank)`。因为向量余弦与 BM25 **量纲不同不可直接比较**，RRF 只看名次、天然跨模态可比。各通道有 `channel-weights` 加权（向量1.0/关键词1.0/图谱0.8/联网0.5）。融合后截断到 `rerank-candidate-limit` 候选池。

**追问：RRF 之后为什么还要 Rerank？**
答：形成**粗排（RRF，便宜）→ 精排（Rerank，贵但准）**两阶段。`RerankPostProcessor` 用交叉注意力模型按"问题-证据"重打分，收敛到最终 `default-top-k(10)`。兼顾成本与精度。

**追问：说说过滤链的顺序？**
答：`SearchResultPostProcessor` 按 `order` 排序：去重（Deduplication，按 `RetrievedChunkKey`=id 否则 SHA-256 文本）→ 融合 RRF(order 5) → Rerank(order 10)。单一处理器异常只跳过自身，不影响整条链。

## 2.6 模型治理（亮点，容易讲出彩）

**问：多个大模型供应商是怎么做高可用的？**
答：`infra-ai` 把所有供应商封装成**统一 `ChatClient` 接口**，配置层定义 tier（fast/standard/deep）→ 候选模型列表（按优先级）。`ModelRoutingExecutor.executeWithFallback` 按序尝试：
- 熔断门控：`ModelHealthStore.allowCall` 拒绝被熔断的候选
- 成功即 `markSuccess` 返回；失败 `markFailure` 并**线性降级到下一个候选**
- 全失败抛 `RemoteException` 触发全局降级

**追问：讲讲三态熔断？**
答：`ModelHealthStore` 里每个模型有 **CLOSED → OPEN → HALF_OPEN** 三态：
- CLOSED 连续失败达 `failureThreshold(2)` → OPEN，冷却 `openDurationMs(30s)`
- OPEN 冷却期内拒绝一切调用，冷却结束**第一个请求转入 HALF_OPEN 探活**
- HALF_OPEN 只放行一个探测请求（`halfOpenInFlight` 互斥），成功→CLOSED，失败→回 OPEN
- 关键：**按 targetId 独立隔离**，一个模型熔断不影响其它模型；并发安全用 `ConcurrentHashMap.compute`

**追问：探测请求谁来放行？**
答：`LlmFirstPacketProbe` 会在首包探测中断时由持有者 `releaseHalfOpenPermit` 释放半开名额，否则半开名额可能被永久占用导致模型"卡在半开"（这也是 git 历史里一个真实修复 #75）。

## 2.7 会话记忆（容易被问）

**问：多轮对话怎么控制 Token 成本又有上下文？**
答：`rag/core/memory` 用**两层记忆**——最近 N 轮（`history-keep-turns=8`）原始消息 + 超过阈值（`summary-start-turns=9`）后触发 **LLM 摘要**（`summary-max-chars=400`），摘要作为 history 第一条 system 消息。两机制共同把上下文体量压住。

**追问：摘要每轮都调 LLM 吗？**
答：不是。真实修复（#56）让它**只在窗口滚动到需要时**才生成/更新摘要，避免每轮滑动都白调一次 LLM、白白增加延迟与成本。

## 2.8 知识生产链路（入库）

**问：一份文档从上传到可被检索，经过哪些阶段？**
答：`DefaultIngestionKernel` 固定五阶段，不可跳过：
`identity(MIME识别) → parse(解析成结构化Block) → chunk(分块) → embed(向量化) → index(落库)`。
- 上传触发 RocketMQ **事务消息** → 消费者异步执行（不在 HTTP 线程里做重活）
- 解析靠 `ParserRegistry`（MIME × 解析档位 二维注册表），Tika/POI/MinerU/VLM 各司其职
- 分块靠 `BlockAwareChunkerDispatcher`（按 Block 类型选 Chunker），`ChunkPacker` 按标题做"章节级打包"
- 落库经 `ChunkSink` SPI 扇出到关系库 `t_knowledge_chunk` + 向量库（pgvector/Milvus），**同一个事务**

**追问：为什么用 RocketMQ 事务消息？**
答：保证"**数据库状态变更**和**消息投递**的最终一致"——先发半消息，本地事务把文档置 RUNNING 后 commit，半消息转正式；本地回滚则 broker 通过 `TransactionChecker` 反向检查文档状态决定 COMMIT/ROLLBACK。避免"消息发出去了但库里没这条文档"或反之。

## 2.9 底层工程能力（容易被挖）

- **分布式 ID**：`CustomIdentifierGenerator` 用 hutool 雪花，workerId 通过 Redis Lua 脚本 `snowflake_init.lua` 原子分配保证多实例不冲突。
- **线程上下文传递**：`UserContext`、`RagTraceContext` 用 **TransmittableThreadLocal**（阿里 TTL），因为 RAG 大量用 `CompletableFuture`/线程池，普通 ThreadLocal 会丢上下文。
- **幂等**：MQ 消费幂等（`IdempotentConsumeAspect` 用 Redis `SET NX GET` 原子占位）+ 请求幂等（`IdempotentSubmitAspect` 用 Redisson 分布式锁）。
- **审计**：集成 `bizlog-sdk`（mzt-log），`@LogRecord` 注解 + SpEL 表达式自动记录操作人/变更快照/前后 diff，写业务变更日志表。
- **鉴权**：sa-token（轻量，比 Spring Security 简单）+ Redis 存储会话，`UserContextInterceptor` 把登录用户灌进 TTL。
- **检索作用域一致性**：`RetrievalScopeResolver` 在**进入通道前算一次**作用域挂到 `SearchContext`，三个通道只读不判，保证同一子问题内三通道检索范围一致。

## 2.10 高频"为什么"速查

| 问题 | 一句话答案 |
|:---|:---|
| 为什么用 RRF 而不是分数平均？ | 跨模态分数量纲不同不可比，RRF 只看名次 |
| 为什么要 Rerank？ | 粗排便宜精排准，两阶段兼顾成本与精度 |
| 为什么线程上下文用 TTL？ | RAG 大量异步并行（CompletableFuture/线程池），普通 ThreadLocal 会丢 |
| 为什么入库用事务消息？ | 保证库状态与消息投递最终一致，避免"半成品" |
| 为什么通道级超时？ | 最慢一路（如联网/图谱）不能拖垮整体多路召回 |
| 为什么意图识别 + 歧义澄清？ | 减少错误检索，让用户一点明比召回一堆噪声省 |
| 为什么分块做"块感知"？ | 普通定长切片会切断标题/表格/代码语义，Block-aware 保住结构 |
| 为什么三态熔断而非两态？ | HALF_OPEN 探活避免服务一恢复就长期处于熔断冻结 |

## 2.11 可以主动讲的"亮点/自省"

1. **检索归因日志**：Rerank 前后按通道统计候选存活，能精准判断"图谱通道是不是纯成本"——这是生产调优的真实抓手。
2. **诚实列出已知短板**（面试加分）：
   - 密码当前是**明文存储比对**（`AuthServiceImpl`），生产必须换 BCrypt + 登录限流
   - 意图树/圈复杂度随规模上升，`MAX_INTENT_COUNT=3` 是硬上限
   - 明文只适合内网 demo，鉴权安全加固是有意的待办
